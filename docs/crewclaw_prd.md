## 1. 背景

现在很多 AI Agent 产品都像“工具箱”：用户要自己找插件、配能力、写提示词、接工具、调权限。问题是，普通用户并不想“组装发动机”，他们只想“招一个能干活的人”。

CrewClaw 要把 Agent 从“插件/工具/模板”重新包装成“AI 员工”。用户不再安装一个冷冰冰的能力包，而是在市场里招聘一个带身份、职责、技能、工具权限和工作说明书的 AI 员工。

CrewClaw 的记忆点是：

> BOSS 直聘 for AI Agent。

它不是 Skill Marketplace，而是 AI Employee Marketplace。

ClawHub 更像“技能商店”，用户买的是能力。CrewClaw 更像“人才市场”，用户雇的是一个可加入团队的 AI 员工。

---

## 2. 产品愿景

让任何人都能像组建人类团队一样组建 AI 团队。

未来用户打开 CrewClaw，不是在想“我需要哪个插件”，而是在想：“我现在缺一个运营助理、销售助理、澳门人脉助手、研究员、客服代表，谁能马上入职？”

CrewClaw 的长期形态是一个可搜索、可雇佣、可组合、可评价、可发布、可交易的 AI 员工市场。

---

## 3. 核心定位

CrewClaw 的核心对象不是工具，而是 Employee Package，也就是 AI 员工包。

一个 AI 员工包由五层组成：

| 层级     | 含义         | 用户感知                                |
| -------- | ------------ | --------------------------------------- |
| Identity | 它是谁       | 名字、头像、职位、所属领域              |
| Soul     | 它怎么工作   | 性格、语气、工作原则、边界              |
| Skills   | 它会什么     | 研究、写作、外联、分析、客服等能力      |
| Tools    | 它能调用什么 | 浏览器、数据库、日历、邮件、API、RAG 等 |
| Manifest | 它的说明书   | 安装要求、权限、版本、输入输出、限制    |

产品要让用户感受到：我不是装了个插件，我是真的招了一个 AI 员工进团队。

## 4. 产品目标

### 4.1 MVP 目标

MVP 要证明一件事：

用户可以从市场里找到一个 AI 员工，理解它的能力，一键雇佣到自己的团队，然后通过命令或界面管理它。

MVP 最小闭环：

发现员工 → 查看员工详情 → 雇佣员工 → 查看团队 → 体检员工 → 解雇员工。

### 4.2 商业目标

CrewClaw 未来可以成为 Agent 创作者的分发平台。创作者负责做 AI 员工，用户负责雇佣，平台负责分发、可信验证、版本管理和交易。

### 4.3 品牌目标

让评委、投资人、用户在 10 秒内记住 CrewClaw：

> 这是一个 AI 员工版 BOSS 直聘。

---

## 5. 非目标

MVP 阶段不做“大而全 Agent IDE”。

暂时不做以下事情：

| 非目标                | 原因                         |
| --------------------- | ---------------------------- |
| 完整在线 Agent 编排器 | 太重，容易拖慢 Demo          |
| 复杂多 Agent 自动协作 | 先证明单个员工可雇佣、可管理 |
| 完整支付结算系统      | 先做免费/模拟价格/内测白名单 |
| 企业级权限体系        | MVP 先做基础权限确认         |
| 通用 Agent 托管云     | 先支持包安装和运行配置       |

## 7. 核心场景

### 7.1 场景一：用户雇佣澳门人脉助手

用户正在做澳门市场拓展，需要一个懂本地行业、会议、社群和潜在客户线索的 AI 员工。

用户在 CrewClaw 搜索 “Macao Networking Agent”，打开详情页，看到它的职位是 “澳门人脉拓展助手”，能力包括线索整理、会议资料搜索、联系人画像、外联话术生成。用户确认权限后点击 Hire，员工加入团队。

成功体验：用户感觉自己不是装插件，而是真的招了一个懂澳门业务的 AI 助手。

### 7.2 场景二：开发者发布一个 AI 研究员

创作者做了一个 Research Agent，希望其他人能使用。创作者提交员工包，填写身份、职责、技能、工具权限、使用限制和示例任务。平台审核通过后，该 Agent 出现在市场里。

成功体验：创作者感觉自己不是上传了一个脚本，而是在平台上发布了一个可被雇佣的 AI 员工。

### 7.3 场景三：用户体检自己的 AI 团队

用户雇了多个 AI 员工后，想知道哪些还能正常工作，哪些缺权限，哪些版本落后。

用户执行 doctor 或在界面点击“体检团队”，CrewClaw 返回每个员工的状态、问题和修复建议。

成功体验：用户能像管理团队一样管理 AI 员工。

## 9. 核心命令设计

CrewClaw 的命令要故意做得像管理团队，而不是像装插件。

| 命令         | 含义         | 用户感知           |
| ------------ | ------------ | ------------------ |
| crew search  | 搜索 AI 员工 | 去人才市场找人     |
| crew hire    | 雇佣 AI 员工 | 员工入职           |
| crew list    | 查看团队成员 | 看当前团队         |
| crew doctor  | 体检员工状态 | 检查是否能正常工作 |
| crew fire    | 解雇 AI 员工 | 移出团队           |
| crew update  | 更新员工版本 | 给员工升级         |
| crew inspect | 查看员工详情 | 看员工简历         |
| crew submit  | 发布员工包   | 创作者投递员工     |

Demo 阶段最重要的命令是：

`crew hire macao-networking-agent`

这个命令要成为舞台记忆点。它表达的不是安装，而是 AI 员工入职。

## 10. 关键用户流程

### 10.1 雇佣 AI 员工流程

入口：市场首页、搜索结果页、详情页、CLI。

流程：

1. 用户搜索或浏览 AI 员工。
2. 系统展示员工卡片。
3. 用户进入员工详情页。
4. 用户查看岗位、能力、权限、评分和示例任务。
5. 用户点击 Hire。
6. 系统展示权限确认。
7. 用户确认。
8. 系统把员工加入用户团队。
9. 系统展示入职成功页。
10. 用户可以马上试一个示例任务。

验收标准：

| 编号        | 标准                                     |
| ----------- | ---------------------------------------- |
| AC-HIRE-001 | 用户能在 3 步内从员工详情页完成雇佣      |
| AC-HIRE-002 | 雇佣前必须展示工具权限和数据访问范围     |
| AC-HIRE-003 | 雇佣成功后，团队列表必须出现该员工       |
| AC-HIRE-004 | 重复雇佣同一员工时，系统要提示已雇佣     |
| AC-HIRE-005 | 雇佣失败时，系统要说明失败原因和修复建议 |

### 10.2 体检 AI 员工流程

入口：团队页、员工详情页、CLI。

流程：

1. 用户点击 Doctor 或执行 doctor 命令。
2. 系统检查员工包完整性。
3. 系统检查工具权限。
4. 系统检查依赖是否存在。
5. 系统检查版本是否过期。
6. 系统返回健康状态。
7. 系统给出修复建议。

健康状态分三类：

| 状态    | 含义                           |
| ------- | ------------------------------ |
| Healthy | 正常可用                       |
| Warning | 可以运行，但存在风险或配置缺失 |
| Broken  | 无法正常运行                   |

验收标准：

| 编号       | 标准                          |
| ---------- | ----------------------------- |
| AC-DOC-001 | doctor 能返回员工整体状态     |
| AC-DOC-002 | doctor 能指出缺失权限         |
| AC-DOC-003 | doctor 能指出缺失依赖         |
| AC-DOC-004 | doctor 能指出版本过期         |
| AC-DOC-005 | doctor 必须给出下一步修复建议 |

### 10.3 解雇 AI 员工流程

入口：团队页、员工详情页、CLI。

流程：

1. 用户选择 Fire。
2. 系统提示影响范围。
3. 用户确认。
4. 系统移除该员工。
5. 系统保留历史记录，但禁止新任务调用。

验收标准：

| 编号        | 标准                                  |
| ----------- | ------------------------------------- |
| AC-FIRE-001 | 解雇前必须二次确认                    |
| AC-FIRE-002 | 解雇后团队列表不再展示该员工为 Active |
| AC-FIRE-003 | 历史日志仍然可查                      |
| AC-FIRE-004 | 解雇后的员工不能继续调用工具          |

### 10.4 发布 AI 员工流程

入口：Creator Console、CLI。

流程：

1. 创作者创建员工包。
2. 填写员工身份、职责、能力、工具权限、限制。
3. 上传或提交 Manifest。
4. 系统进行基础校验。
5. 平台进入审核队列。
6. 审核通过后发布到市场。
7. 员工详情页展示 Verified 状态。

验收标准：

| 编号          | 标准                           |
| ------------- | ------------------------------ |
| AC-SUBMIT-001 | 必填字段缺失时不能提交         |
| AC-SUBMIT-002 | 高风险权限必须被标记           |
| AC-SUBMIT-003 | 审核通过前不能公开出现在主市场 |
| AC-SUBMIT-004 | 发布后能通过搜索找到           |
| AC-SUBMIT-005 | 发布后能被正常雇佣             |

| 编号   | 需求               | 优先级 |

### 14.3 雇佣员工

| 编号   | 需求                    | 优先级 |

用户要能知道员工能不能正常运行。

| 编号   | 需求                 | 优先级 |
| ------ | -------------------- | ------ |
| FR-023 | 检查 Manifest 完整性 | P0     |
| FR-024 | 检查权限是否授权     | P0     |
| FR-025 | 检查工具依赖是否存在 | P0     |
| FR-026 | 检查版本是否过期     | P1     |
| FR-027 | 返回修复建议         | P0     |

| 编号   | 需求               | 优先级 |

| FR-031 | 支持进入审核队列   | P0     |
| FR-032 | 支持发布成功后上架 | P0     |
| FR-033 | 支持版本更新       | P1     |

验收标准：创作者提交一个字段完整的员工包后，平台可以审核并发布，用户能搜索和雇佣。

### 14.7 审核与安全

平台要防止恶意员工包进入市场。

| 编号   | 需求                      | 优先级 |
| ------ | ------------------------- | ------ |
| FR-034 | 标记高风险权限            | P0     |
| FR-035 | 禁止未说明的数据写入权限  | P0     |
| FR-036 | 审核通过后才显示 Verified | P0     |
| FR-037 | 支持下架员工              | P0     |
| FR-038 | 支持用户举报              | P1     |

验收标准：任何请求邮件发送、联系人写入、支付操作、删除数据的员工，都必须被标为高风险权限，并在 Hire 前明确提示。

## 15. 权限与安全设计

CrewClaw 的信任感很关键。用户雇佣 AI 员工时，最怕它乱动数据。所以权限要讲人话，不要只显示技术名。

### 15.1 权限等级

| 等级                    | 含义       | 示例                   |
| ----------------------- | ---------- | ---------------------- |
| Read-only               | 只读       | 读取网页、读取公开资料 |
| Write with confirmation | 写入前确认 | 起草邮件但不自动发送   |
| Autonomous write        | 可自动写入 | 自动更新 CRM 字段      |
| Sensitive action        | 高风险操作 | 发邮件、付款、删除数据 |

MVP 默认只支持前两类。高风险权限可以展示，但不默认开放。

### 15.2 Hire 前权限提示

雇佣前必须展示：

| 信息             | 说明                   |
| ---------------- | ---------------------- |
| 它要访问什么     | 数据范围               |
| 它能做什么动作   | 只读、写入、发送、删除 |
| 哪些动作需要确认 | 用户确认点             |
| 风险是什么       | 可能的错误或误操作     |
| 如何撤销         | 解雇或关闭权限         |

## 16. 员工生命周期

AI 员工从创建到被使用，有完整生命周期。

| 状态      | 含义             |
| --------- | ---------------- |
| Draft     | 创作者草稿       |
| Submitted | 已提交审核       |
| Rejected  | 审核未通过       |
| Published | 已上架           |
| Verified  | 已认证           |
| Hired     | 被用户雇佣       |
| Active    | 在用户团队中可用 |
| Warning   | 可用但有问题     |
| Broken    | 不可用           |
| Fired     | 已被解雇         |
| Disabled  | 平台下架或禁用   |

生命周期最重要的体验点是：

发布是创作者视角，雇佣是用户视角，体检是使用后管理视角。

## 24. 技术假设

MVP 可以采用“市场前端 + 包注册表 + CLI + 简单运行时检查”的方式实现。

| 模块         | 假设                                           |
| ------------ | ---------------------------------------------- |
| Marketplace  | Web 页面展示员工列表和详情                     |
| Registry     | 存储员工包和 Manifest                          |
| CLI          | 支持 hire / list / doctor / fire               |
| Runtime      | 先不做完整云运行，只做本地或模拟集成           |
| Permission   | 先做声明式权限确认                             |
| Review       | 先做人工审核状态                               |
| ClawHub 集成 | Skills 可以来自 ClawHub，CrewClaw 负责员工封装 |

关键原则：MVP 要先证明产品概念，不要被完整基础设施拖死。

## 30. 最终判断

CrewClaw 最该死磕的不是“Agent 功能有多强”，而是“招聘 AI 员工”这个心智。

只要用户和评委能在第一眼明白：

> 我可以在这里招聘一个 AI 员工加入我的团队。

这个产品就立住了。

MVP 不需要先做成全世界最强 Agent 平台。它先要做到一件事：

让 AI Agent 从工具变成员工，从安装变成雇佣，从插件市场变成人才市场。
